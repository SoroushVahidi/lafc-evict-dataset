\section{Benchmark Tasks and Baselines}
\label{sec:tasks-baselines}

\lafc\ supports four benchmark tasks from one release.

\paragraph{Candidate-level value prediction.}
Predict \texttt{y\_loss} or \texttt{y\_value} from a single candidate row. This is a pointwise task over the canonical benchmark unit and measures how well a model predicts finite-horizon counterfactual eviction quality for one candidate at one decision.

\paragraph{Best-candidate selection.}
Given all candidate rows for one decision, identify a member of the minimum-loss set. This task can be framed as ranking or decision-level classification and connects most directly to the actual cache-eviction choice because it evaluates whether a method selects a benchmark-optimal victim within that decision.

\paragraph{Pairwise preference prediction.}
Predict whether candidate A is better than candidate B within the same decision, where ``better'' means lower \texttt{y\_loss} or equivalently higher \texttt{y\_value}. This task uses the pairwise view or shipped pairwise sample as a simpler interface for within-decision preference modeling. Because equal losses induce ties, reports must state whether evaluation includes ties, excludes them, or treats them as a separate class. In the shipped sample, deterministic hash randomization of A/B orientation keeps the non-tie A-better/B-better split balanced (about 49.8\%/50.2\%) rather than encoding candidate-identifier order.

\paragraph{Candidate-label distribution characterization.}
Summarize the empirical label distributions without training a predictive model. This characterization task studies distributions of \texttt{y\_loss}, \texttt{y\_value}, regret, tie frequency, and decision ambiguity across families, capacities, horizons, and splits. It is descriptive rather than competitive, but it is important for understanding benchmark difficulty and for interpreting downstream task results.

The empirical scope of this paper remains intentionally narrow. Rather than presenting a large model bake-off, we report lightweight baselines that can be executed directly from the committed release views and that establish reproducible reference points for later work.

\begin{sloppypar}
The current results cover three such references. A linear regression baseline over candidate rows predicts \texttt{y\_loss} from released features. It is intentionally weak: test MAE is 3.8739 with RMSE 4.7152 and $R^2=0.0026$, and the validation-split $R^2$ is slightly negative ($-0.0506$). Using that same linear score for within-decision selection nevertheless provides a reproducible decision-level floor. On the pairwise task, the earlier random and majority non-tie results remain useful sanity checks, but by themselves they do not test whether the released candidate features contain decision-relevant signal.
\end{sloppypar}

\paragraph{Candidate-feature quality disclosure.} Of the 26 released
candidate-level feature columns, a full-corpus audit (277,995,072 rows)
found that 19 are uninformative: 18 are globally constant and one is
bit-identical to another column. The cause is an upstream generator bug --
an annotation step these columns depend on never runs before feature
extraction, so they silently receive a hardcoded default -- not a modeling
choice, so we deprecate all 19 from the modeling feature set rather than
reconstruct them (reconstruction would require a routine that uses
ground-truth future arrival time, which would leak future information into
columns the benchmark otherwise keeps online-computable). Only 7 columns
(\texttt{candidate\_recency\_rank}, \texttt{candidate\_age\_norm},
\texttt{candidate\_lru\_score}, \texttt{candidate\_is\_lru\_victim},
\texttt{score\_gap\_to\_lru\_victim}, \texttt{recent\_candidate\_request\_rate},
\texttt{recent\_candidate\_hit\_rate}) remain. Refitting every baseline
below on only these 7 columns reproduces the reported numbers exactly for
two baselines and within a few tenths of a percentage point for the other
two, confirming the 19 deprecated columns contributed no measurable signal
to any result reported here. Full audit and root cause:
\texttt{analysis/feature\_provenance\_repair\_20260917/}.

To test whether released candidate features carry pairwise signal without
changing the benchmark schema, we join those features back to the capped
shipped pairwise sample for evaluation only. This remains a sample-backed
evaluation, not a full quadratic pairwise materialization. The canonical
regenerated sample is itself tie-heavy: 878,262 of 1,000,000 rows (87.8\%)
are exact ties, leaving 121,738 non-ties. All classifier metrics below are
therefore non-tie-only.

\textbf{Fitting and evaluation protocol.} Logistic score calibrations and
the feature-difference model are fit only on non-tie \texttt{train} rows,
with fixed L2 regularization and no validation tuning. The temporally
held-out \texttt{test} split is the generalization result; train/validation
columns are diagnostic. On the 2,211-row test non-tie subset, the logistic
feature-difference model reaches 0.7078 accuracy and 0.5494 log loss,
ahead of random/majority checks and the 1-D score baselines
(Table~\ref{tab:pairwise-feature-baselines}). This replaces the earlier
overall non-tie 0.9660 figure as the number to cite. The train/validation
gap is large, and the test non-tie subset is small and unusually tie-heavy,
so the result supports only a capped-sample, non-tie pairwise baseline,
not a population or online-policy claim.

The best-candidate evaluator groups candidate rows by the canonical
9-column decision key and reports 2,363,286 decisions, an exact match
with the decision view (Section~\ref{sec:benchmark-design}). Because many
decisions have exact ties, top-1 optimal-set selection rate is not a
sufficient primary metric: a uniform-random selector's expected
optimal-selection rate is already 0.9912 with expected regret 0.0088.
Accordingly, the decision-level utility analysis in
Section~\ref{sec:characterization} treats ties as genuine equal optima and
uses realized regret, stratified by expected random regret, as the primary
selector-quality view. In that analysis random is evaluated analytically;
LRU chooses the released LRU victim; the clean linear selector uses the
Problem-2 seven-feature least-squares loss model; the clean pairwise
selector uses the Problem-2 strict-preference feature-difference logistic
model as a within-decision score; and the frozen HGB artifacts are scored
with their original loss-prediction orientation. Equal-loss pairs are never
converted into arbitrary wins or losses.
